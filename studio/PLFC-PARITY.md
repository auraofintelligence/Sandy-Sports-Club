**Single source of truth for the Sandy build.** This replaces the earlier Social Studio-only parity comparison. The target is the equivalent useful club platform, adapted to Sandy Sports, not a visual copy, a collection of forms, or a clone of fishing-specific content.

This is a source and existing test-evidence review, not a complete line-by-line PLFC port, authenticated live-browser audit or formal security assessment. Statuses are deliberately conservative.

## Non-negotiable owner requirements

- Build the equivalent end-to-end PLFC functionality in Sandy's own design and terminology, without copying irrelevant fishing content, actual club data, phishing/deceptive features, private source documents, credentials or branding. Exclude deceptive interfaces, credential harvesting and unsafe third-party connections, not legitimate secure sign-in and scam-awareness features.
- Preserve existing Sandy Cloudflare Worker, D1, real Webmaster account and existing records. No database recreation, bootstrap repeat, credential reset, or changes to PLFC.
- Reserve office-holder accounts but **no active invitations or outgoing invites** until explicitly authorised. Verify existing reservations privately; do not invent live account state.
- Exactly one synthetic preview-only member profile, not a member login. Real Webmaster has full authorised administration plus accurate role-layout previews. Provide a separately usable view-only Webmaster demo with synthetic data only.
- No real member enrolment, formal club decisions, financial collection, outbound email/SMS, automatic publishing, paid advertising, external commissions, or partner transfer until separately authorised. Keep current production gates disabled.
- Sandy membership classes and fees remain for the owner to decide. Do not copy PLFC prices or claim Sandy has registered, adopted rules, appointed officers, venue rights or approved events.
- No em dashes in new or modified text. Avoid gratuitous rewrites, repeated shell changes, fabricated records or creating another parallel planner. Keep existing local drafts available for reviewed migration.
- Build complete cohesive workflow groups. A page, table, field schema, button, menu, isolated test or commit is not sufficient proof of functionality.

## How to use this matrix

Each row is a functional acceptance unit, not a count of pages. P0 is a blocking safety/identity foundation; P1 is required core operational parity; P2 is deeper/conditional functionality, including appropriately deferred integrations. These are suggested development priorities, not permission to activate real services. Owner approval controls launch and policy decisions.

| Status | Meaning |
| --- | --- |
| Blocked | A concrete implementation problem or dependency prevents a valid acceptance claim. |
| Gap | No comparable complete functional path identified in reviewed Sandy source. |
| Partial | Useful working code or structured workflow exists, but major behavior is missing or unverified. |
| Substantial | Significant equivalent implementation and some automated evidence exist, but all acceptance criteria are not yet independently verified. |
| Hold | Intentionally excluded or disabled, or dependent on a separate owner decision. Must not be silently activated. |
| Accepted | All row-specific and common acceptance gates have evidence, and any production activation is separately authorised. None is claimed at baseline. |

**Baseline counts:** 79 acceptance units; 12 P0, 53 P1, 14 P2. 5 blocked, 15 gap, 51 partial, 6 substantial, 2 hold, 0 accepted. Counts are not a percentage-complete metric; rows vary significantly in effort.

**Current branch counts (Gate A record privacy and showcase):** 79 acceptance units; 1 blocked, 13 gap, 52 partial, 11 substantial, 2 hold, 0 accepted. These counts describe the proposed branch, not deployed production.

## Common definition of done for every row

1. **Complete workflow:** an authorised person can discover the tool, begin with correct context, enter/select meaningful data, validate, save, reopen, edit, cancel or complete, and reach the next relevant workspace. No fake success, placeholder screen or disconnected form. Where appropriate support export, print, archive and correction.
2. **Single source of truth:** related desks refer to the same stable record ID. Events, member records, tasks, assets, costs, notices and publication states remain consistent without manual re-entry or contradictory duplicate records.
3. **Authorisation:** actual server-side role, owner, permission and purpose checks for every read/write and alternate route. Signed-out, wrong-role, demo and other-member tests; negative tests cover direct URLs, IDs, histories, exports, counts, generic routes and embedded tools. A UI role switch is not an access control.
4. **Persistence and audit:** durable isolated Sandy D1, actual authenticated actor/office, timestamps, versions, auditable changes, atomic linked writes, retries/idempotency, conflict handling, refresh/new session and schema-safe migration. Clear browser-local versus server-saved messaging.
5. **Data safety:** fictional fixtures in automated and demo tests, no production private data in code, snapshots or public output. Preserve existing records, privacy choices and provenance. No unauthorised outbound service or spending.
6. **Usability:** realistic phone and desktop workflows, keyboard/focus, readable labels and errors, responsive layout, understandable help and role-appropriate navigation. Tests must verify interaction, not just DOM element existence.
7. **End-to-end evidence:** focused automated positive/negative integration tests using isolated SQLite/D1; browser acceptance on an authorised isolated preview or owner-approved non-destructive live review. Record test paths, run URL, commit, scenario result, known limitations and deployment actually checked. A green general CI run alone is not sufficient.
8. **Acceptance:** update the row only when its specific scenario and applicable common gates have evidence. Do not claim production readiness from a mock, screenshot, schema or source-only check. Mark unresolved and conditional requirements explicitly. Legal adoption, actual appointments and external activation are separate decisions.
